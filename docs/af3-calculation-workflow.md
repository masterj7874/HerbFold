## 화면에서 사용하기

**다른 단백질 표적:** UniProt ID를 조회·등록한 뒤 적용하면 해당 단백질 이름·생물종·서열 길이를 확인하고 계산에 사용할 수 있습니다. 등록과 적용은 계산을 자동 실행하지 않습니다. 등록 서열은 저장되며, 각 계산은 준비 당시 서열과 출처를 보존합니다. [UniProt 표적 사용법](uniprot-targets.md).

1. 분자 스튜디오에서 계산할 물질을 선택하고 **저장된 AF3 예측**으로 전환합니다. 계산 패널에 선택 물질과 표적이 표시됩니다.
2. MSA 모드와 seed를 지정합니다. 기본은 공식 DB를 검색하는 모드입니다. DB가 없다고 자동으로 생략하지 않습니다. **MSA·template 미사용**은 설명 확인 후 직접 선택하는 탐색 모드입니다.
3. **입력 준비**를 누르면 정확한 리간드 SMILES와 표적 전체 서열로 별도 작업을 저장합니다. 입력 JSON과 실행을 막는 조건을 확인할 수 있습니다.
4. 실행 조건을 만족한 작업에서 **계산 실행**을 누릅니다. AF3 작업은 한 번에 하나씩 실행되며 대기 순번과 로그를 표시합니다. 실행 중 다른 물질의 작업을 준비하고 대기열에 넣을 수 있습니다.
5. 완료 후 그 작업의 결과를 분자 스튜디오에서 확인합니다. 물질·표적이 바뀌면 이전 작업의 늦은 응답을 표시하지 않습니다. 작업 선택 메뉴로 같은 물질의 seed·모드별 결과를 다시 볼 수 있습니다.
6. 실패·차단·중단 작업은 **같은 조건으로 다시 준비**하여 재시도합니다. 새 작업은 이전 작업 ID를 기록하고 기존 출력과 로그를 보존합니다. 새로고침 후 같은 브라우저 탭에서 선택 물질과 작업을 복원합니다.

실행 중인 동일 요청을 여러 번 준비해도 중복 작업을 만들지 않습니다. 물질, 표적 전체 서열, seed, MSA 모드, AF3 설정, 파라미터 파일 상태, 검증 DB 지문과 자식 프로세스 환경을 요청 식별에 포함합니다. 같은 물질로 추가 표본이 필요하면 seed를 바꾸세요. 입력 준비 후 가중치나 환경이 바뀌면 해당 작업은 실행 전에 다시 차단되고 새 입력 준비가 필요합니다.

## 표준 MSA·템플릿 검색과 재사용

전체 DB는 공식 8개 FASTA와 `mmcif_files` 트리, 해당 트리 inventory를 갖춰야 합니다. 설치기는 다운로드 전체 CRC32C·MD5, 압축 해제, 전체 형식·레코드 수와 SHA-256을 확인한 뒤에만 `official_databases_manifest.json`의 `status=complete`를 기록합니다. 실행 준비는 이 기록의 v3.0.4/commit, 필수 구성 요소와 파일의 크기·inode·수정/변경 시각을 확인합니다. 요청마다 수백 GB 전체를 다시 해시하는 검사는 아닙니다. 운영 중 DB와 inventory를 변경했다면 설치 검증을 다시 수행해야 합니다. RNA 파일도 공식 launcher가 경로를 확인하므로 단백질 전용 요청에서 생략할 수 없습니다. [공식 DB 계획](af3-msa-db-plan.json), [공식 설치 스크립트](https://github.com/google-deepmind/alphafold3/blob/v3.0.4/fetch_databases.sh).

다른 저장소에서 설치를 재현할 때는 충분한 공간이 있는 실제 절대 경로를 지정합니다. 설치기의 CRC32C·zstd 의존성은 프로젝트의 `databases` extra와 `uv.lock`에 고정했습니다.

```bash
uv run --locked --extra databases python scripts/install_af3_databases.py --directory /absolute/path/to/alphafold3_databases/v3.0
```

공식 압축 파일 약 238.784 GB와 설치 본문 약 672.435 GB를 함께 보존하며 여유 공간도 필요합니다. 같은 명령을 다시 실행하면 미완료 다운로드의 실제 파일 크기·해시를 확인한 뒤 이어받습니다. `.installation/status.json`에서 진행 상태를 확인합니다. 새 설치를 검증한 뒤에는 `.env`의 `AF3_DB_DIR`을 해당 디렉터리로 설정하고 서버를 재시작합니다. 현재 운영 저장소는 이 설정과 재시작을 이미 마쳤습니다.

스튜디오의 단일 단백질 체인은 다음 순서로 실행합니다.

1. 원래 `fold_input.json`에 MSA·template 필드를 넣지 않은 상태로 보존합니다. 캐시가 없으면 `--run_data_pipeline=true --run_inference=false`로 **CPU 검색**만 먼저 실행합니다. native 자식은 GPU를 숨기며, Docker 검색 컨테이너에는 GPU를 노출하지 않습니다. HMMER는 공식 3.4 및 AF3 `seq_limit` 패치가 있는 실행 파일을 사용합니다.
2. 성공 종료 후의 `*_data.json`에서 전체 query 서열, 각 A3M 정렬 길이, 두 MSA의 실제 레코드, template mmCIF 좌표와 잔기 매핑을 검사합니다. 누락·빈 MSA, 잘못된 서열, 잘못된 매핑 또는 일부 출력만으로는 추론을 시작하지 않습니다. 검색이 실제 완료됐지만 query만 있거나 적합한 template가 0개인 경우는 측정값과 경고를 그대로 남깁니다.
3. 검증된 단백질 필드만 내부 `inference_input.json`에 넣고 **현재 선택한 리간드·seed**를 유지합니다. 이후 `--run_data_pipeline=false --run_inference=true`로 AF3 추론을 수행합니다. 이는 검색을 생략한 `none` 모드로의 변경이 아닙니다.
4. 다음 리간드는 동일한 전체 단백질 서열 SHA, DB 설치 지문, AF3 버전·commit·entrypoint 또는 고정 Docker 이미지, HMMER 파일 상태, template 날짜와 캐시 스키마가 일치할 때만 같은 단백질 자료를 사용합니다. 리간드와 seed는 단백질 feature 캐시 키에 넣지 않지만 개별 추론 작업의 식별에는 포함합니다. 각 리간드는 별도 추론과 실제 출력 검사를 거칩니다.

캐시는 `HERBFOLD_DATA_DIR/af3-protein-features/{key}/`에 저장합니다. 원본 검색 파일은 첫 작업의 `data_pipeline/`에 남습니다. 완성된 두 파일(`protein_features.json`, `manifest.json`)만 원자적으로 게시하며, 다시 사용할 때 feature SHA-256과 서열·정렬·template를 검증합니다. 손상·미완료본은 사용하지 않고 새 검색을 수행하며 손상본을 별도 보존합니다. 캐시 출처 작업이 실패했더라도 이미 성공적으로 끝난 검색 자료는 다음 명시적 재시도에서 재사용할 수 있습니다.

같은 실행 잠금 안에서 CPU 검색과 추론을 순차 실행합니다. 검색 중 서버 감시가 끊기면 작업은 `interrupted`가 되고 자동으로 재계산하지 않습니다. 완료 캐시가 없으면 새 재시도 작업에서 검색부터, 있으면 해당 단백질 자료를 검사한 뒤 추론부터 진행합니다. 남은 프로세스가 살아 있으면 중복 재시도를 막습니다. 긴 CPU 검색 이후 가중치 파일이나 자식 실행 설정이 바뀐 경우도 추론을 시작하지 않습니다. `AF3_TIMEOUT_SECONDS`는 **검색과 추론을 합친** 시간 상한입니다.

실행 화면에는 현재 CPU 검색/GPU 추론 단계, 단계 경과 시간, 완료된 단계의 실제 소요 시간과 마지막 상태 확인 시각을 표시합니다. 상태와 로그는 독립적으로 조회하므로 로그 응답이 지연돼도 완료 상태를 갱신합니다. 조회는 15초 제한 후 연결을 다시 확인하며, 준비·실행 응답이 지연되면 서버 접수 여부를 확인하도록 안내합니다. 응답 지연만으로 같은 계산을 자동 재제출하지 않습니다.

인증 토큰을 입력한 뒤 **연결 상태 새로 고침**을 누르면 계산 목록·구조·진단도 다시 조회합니다. 탭 복귀와 연결 회복 시에는 작업 상태를 즉시 확인합니다. 구조 응답에는 30초 제한을 두어 무한 대기를 해제합니다. 화면 데이터 수신 시각과 실행 프로세스 확인 시각은 따로 표시하며, 완료 후에는 실제 소요 시간을 고정해서 보여줍니다. 새 실행에서는 버퍼링 없이 전달되는 실제 AF3 로그의 세부 단계와 검색 완료 기록도 표시합니다. [재연결·진행 표시 수정과 검증](af3-loading-reconnect.md).

GPU 메모리 할당 경고는 실행 중 화면에 표시하고, 최종 실패 시 로그 근거와 종료 이유를 보존합니다. 새 할당 실패 메시지만 계속 나타나고 다른 로그 진행이 없는 경우 `AF3_GPU_ALLOCATION_RETRY_TIMEOUT_SECONDS`로 정한 시간 후 해당 추론을 중단합니다. 기본은 180초이며 0으로 끌 수 있습니다. 로그가 조용하다는 이유만으로 중단하지 않고, 다른 진행 메시지·로그 교체·관측 공백이 있으면 연속 실패 관측을 초기화합니다. 기존 입력, 완료된 MSA·템플릿 검색 결과와 로그는 보존됩니다. 재시도 전 GPU 메모리 사용량을 확인해야 하며, 다른 프로그램은 자동으로 종료하지 않습니다.

API 상태 응답의 `stage`는 CPU 검색·추론·출력 확인을 구분합니다. `msa_features`에는 실제 query 포함 unpaired/paired 서열 수, unpaired의 query 외 서열 수, template 수, cache hit, 출처 작업 ID, DB·feature 해시와 검색 실행 시간을 기록합니다. 아직 측정하지 않은 수는 `null`입니다. template별 entry ID/data block, mmCIF SHA와 query/template 매핑도 보존해 실험 비교 구조와 겹치는지 확인할 수 있습니다. 다중 단백질의 기존 expert/legacy API 입력과 분석 오케스트레이터의 동기 실행 경로는 공유 캐시 없이 원래 combined 경로를 유지합니다. 캐시 재사용 검증 범위는 스튜디오와 AF3Queue를 사용하는 API입니다.

## 결과가 의미하는 것

- 작업의 **완료**는 프로그램 실행과 출력 읽기가 끝났다는 뜻입니다. 구조 품질이나 약효·안전성이 검증되었다는 뜻이 아닙니다.
- 결과의 실제 원자·결합 그래프가 요청한 리간드와 일치하는지, 관측된 단백질 서열이 등록된 전체 표적과 일치하는지 확인한 뒤 해당 작업의 구조를 표시합니다. 다른 물질의 결과를 대체 표시하지 않습니다.
- 구조 품질 경고와 물질·표적 불일치를 별도로 표시합니다. 친화도, 약효, 독성을 AF3 신뢰도에서 만들어내지 않습니다.
- 실험 복합체는 해당 실험 물질에 대한 원본입니다. 새로운 물질을 계산해도 기존 실험 좌표를 바꾸거나 실험 결과로 표시하지 않습니다.

## API와 운영

| 요청 | 용도 |
| --- | --- |
| `POST /api/molecular/predictions/prepare` | `{smiles,target_accession,msa_mode,seeds,exploratory_ack,retry}`로 준비 |
| `GET /api/molecular/predictions?smiles=…&target_accession=…` | 해당 물질·표적의 최근 20개 계산 기록 |
| `GET /api/molecular/predictions/{id}` | 상태·대기 순번·입력·검증 결과 |
| `POST /api/molecular/predictions/{id}/execute` | 명시적 실행 제출 |
| `GET /api/molecular/predictions/{id}/log` | 최대 64 KiB의 최신 로그 |
| `GET /api/molecular/predictions/{id}/scene` | 지정한 작업의 물질·표적 일치를 검사한 3D 구조 |

기본 표적은 사람 PTGS2/COX-2 `P35354`, 전체 604개 잔기입니다. 등록된 검증 서열이 없는 표적은 준비하지 않습니다. 서버 API는 요청당 최대 5개 seed를 지원하며 UI에서는 한 개를 지정합니다. 실행 중·대기 작업은 최대 32개입니다. 대기열은 SQLite에 보존되고 재시작 후 복구됩니다. 실행 중 감시가 끊긴 작업은 `interrupted`로 보존하고 자동 재실행하지 않습니다. 프로세스 식별과 실행 잠금은 남은 AF3 자식 프로세스와 중복 추론이 겹치는 것을 막습니다.

## 검증 범위

최종 소프트웨어 검사에서 **Python 테스트 483개 통과, 실패·건너뜀 0개**, Ruff, wheel 및 프런트엔드 빌드를 확인했습니다. [소프트웨어 검증 기록](af3-msa-software-verification.json). CPU 시험 프로그램의 제어 흐름 검사 외에 이번에는 실제 DB 검색, 캐시 재사용, 두 물질의 별도 GPU 추론과 원본 결과 비교까지 완료했습니다. 실제 비교기는 원본 입력과 AF3의 `*_data.json`, feature·template 해시·매핑, 5개 표본과 최상위 복사본의 일치, 원본 ranking CSV, 같은 Cα 집합을 검증했습니다. [실제 원본 비교 기록](af3-msa-structure-comparison.json). 이 검증 통과는 약효·안전성이나 독립적인 구조 정확도 인증이 아닙니다.

[기존 브라우저 검증 기록](af3-studio-ui-verification.json)은 공식 가중치 교체 전에 실제 서버에서 잘못된 가중치 차단, 물질별 준비, 새로고침 복원, 재준비, 실행 API의 409 거부와 모바일 가로 넘침 없음을 확인한 기록입니다. 당시 실제 새 학습 모델 예측 수는 **0**이었습니다. 이후 공식 가중치로 완료한 미사용 baseline 2개 작업·10개 표본과 이번 MSA 사용 2개 작업·10개 표본은 각각의 계산 기록에서 구분하며, 모두 독립적인 품질 인증을 통과했다는 뜻은 아닙니다.

별도 포트·저장소·CPU 프로그램을 사용하는 명시적 시험 환경에서 아스피린/퀘르세틴의 독립 실행, 대기, 완료, 정확한 작업 결과 연결, 실패·재시도, 로그와 작업 재선택을 검사했습니다. 화면에 합성 CPU 시험이라는 배너를 표시하며 이 결과를 운영 예측 데이터에 넣지 않습니다. 이 시험은 제어 흐름 검증이며 실제 AF3 계산이나 구조 정확도 검증이 아닙니다. 재현 도구는 `tests/helpers/af3_studio_fixture_server.py`와 `scripts/verify_af3_studio_ui.py`입니다.
