# 대규모 천연물 카탈로그: 저장 구조와 검증 범위

이 문서는 `DiscoveryCatalog`의 저장·가져오기·순회 동작을 설명합니다. 원천 문헌의 출현 기록 수, 중복 제거된 구조 수, 새로 생성한 계산 후보 수는 서로 다른 수치입니다. 여기서 측정한 행 처리량은 신약 개발 성과나 AlphaFold 3·양자 연산 처리량을 의미하지 않습니다.

## 구현된 저장 구조

`runtime/discovery/discovery.sqlite3`에 다음 정보를 디스크로 저장합니다.

- `discovery_compounds`: RDKit canonical isomeric SMILES, 전체 standard InChIKey, 표시 이름, 원천이 제공한 분자식. 구조 식별에는 전하·동위원소·염 구성 성분을 유지합니다. 같은 표준 InChI를 공유하는 호변이성질체는 같은 identity로 합쳐질 수 있으므로 원본 구조는 provenance에서 확인해야 합니다.
- `discovery_provenance`: 출처, 원천 식별자, 생물 정보, 라이선스, 원천 URL, 가져온 시각, 전체 원본 필드. 같은 원천 식별자라도 원문 내용이나 라이선스·URL이 바뀌면 다른 기록으로 보존합니다. 같은 분자의 다른 생물·논문 출현 기록도 합쳐서 버리지 않습니다.
- `discovery_search`: 원천 식별자·명칭·동의어·생물명·분류군·InChIKey의 SQLite FTS5 인덱스.
- `discovery_stats`, `discovery_sources`, `discovery_imports`: 전체·원천별 누적 카운터와 가져오기 진행 상황. 전체 수 조회에는 매번 전 테이블을 세지 않습니다.

CSV, TSV, SMI, SDF와 각각의 gzip 파일을 순차적으로 읽습니다. 기본 500개 입력 행마다 진행 보고와 커밋을 수행하며, 구조 식별 결과 캐시는 최대 8,192개입니다. 전체 파일을 메모리에 올리거나 전체 화합물 간 모든 쌍을 미리 만들지 않습니다. 가져오기 단계에서는 3D 좌표·결합 친화도·QED·ADMET 등을 계산하지 않습니다.

대용량 원천의 생물명은 원천에서 보고한 정보입니다. 식물·진균·세균·해양 생물 등을 모두 포함할 수 있으므로 천연물 전체를 한약 성분으로 자동 분류하지 않습니다.

## 대량 순회와 재개

일반 화면용 `list_compounds`는 최대 500개를 반환합니다. 매우 깊은 `offset`이나 광범위한 검색의 정확한 전체 개수 계산에는 비용이 들 수 있습니다. 대량 작업에서는 아래의 기본키 커서 방식으로 순회합니다.

```python
from pathlib import Path
from herbfold.discovery_catalog import DiscoveryCatalog

catalog = DiscoveryCatalog(Path("runtime/discovery"))
for compound in catalog.iter_compounds(
    source="lotus-2026-04",
    batch_size=500,
    after_id=0,             # 이전에 처리한 마지막 compound id를 저장해 재개
    through_id=None,        # 기본값은 순회 시작 시 커밋된 최대 id
    include_sources=False, # 구조 중심 작업은 상세 출처 조회 생략 가능
):
    process(compound)       # 호출 측이 처리 결과와 마지막 id를 함께 저장
```

이 메서드는 `OFFSET`이나 전체 `COUNT` 없이 다음 id부터 읽습니다. 출처만 지정한 경우 `(source_id, compound_id)` 인덱스에서 서로 다른 compound id를 묶고 페이지 제한을 적용합니다. 한 물질의 출현 기록이 많아도 물질 자체는 한 번만 반환합니다. 실제 쿼리 계획에서 해당 covering index 사용을 확인했습니다.

배치마다 읽기 연결을 닫은 뒤 결과를 전달합니다. 시작 시의 id 상한으로 순회가 끝나므로 동시에 진행하는 가져오기가 작업 범위를 계속 늘리지 않습니다. 이는 구조 id 범위를 고정하는 방식이며, 전체 provenance의 장시간 트랜잭션 스냅샷을 제공하지는 않습니다. `search`와 `source`를 함께 지정하면 해당 출처의 provenance에서 검색어가 일치하는 구조를 반환합니다. 매우 광범위한 FTS 검색은 각 배치에서 많은 일치 기록을 읽을 수 있습니다.

화면 목록은 화합물당 간단한 출처 최대 10개, 단건 상세는 provenance 최대 1,000개를 반환합니다. 상세 응답에는 실제 provenance 수와 잘림 여부가 포함됩니다.

## 실제 측정

2026-09-07, 이 작업 공간에서 RDKit 2026.03.6으로 [LOTUS 2026-04 공개 릴리스](https://zenodo.org/records/19360665)의 실제 압축 CSV를 가져왔습니다. 원본 필드와 라이선스는 카탈로그에서 보존합니다.

| 측정 | 결과 |
| --- | ---: |
| 초기 5,000행 가져오기 | 2.251초, 약 2,217행/초 |
| 초기 5,000행의 고유 구조 | 1,460개 |
| LOTUS 전체 처리 행 | 709,740행 |
| LOTUS 전체 고유 구조 | 227,265개 |
| LOTUS 전체 고유 출현 기록 | 694,270개 |
| LOTUS 전체 중복 원천 기록 | 15,470개 |
| LOTUS 전체 잘못된 구조 | 0개 |
| LOTUS 전체 가져오기 시간 | 409.962초, 약 1,731행/초 |
| 출처 지정 커서 순회 50,000구조, 상세 출처 제외 | 0.123초 |

50,000개 읽기 측정은 같은 호스트에서 이미 사용 중인 데이터의 인덱스·캐시를 활용한 단일 실행입니다. 디스크 콜드 캐시, 원격 호출, 상세 provenance 조회, 여러 클라이언트의 동시 요청 성능을 보장하지 않습니다. 근거는 `discovery-storage-benchmark.json`과 영속적인 `discovery_imports` 보고서에 기록했습니다.

자동 테스트는 구조 중복 제거, 이성질체 구분, provenance 갱신 보존, LOTUS·COCONUT 필드, gzip·SDF, 동시 가져오기 카운터, 배치 커밋, 입력 상한, 부분 실패, 상세 크기 제한, 커서 재개·중복 제거·동시 추가 중 유한 종료를 확인합니다.

## 수억 건에서 남는 한계

**1억 건을 실제 적재하거나 부하 시험하지 않았습니다.** 행 수 상한을 크게 설정할 수 있는 것과 그 양의 작업을 검증한 것은 구분해야 합니다.

LOTUS만 가져오던 중간 관측에서 220,938구조·656,839출현 기록이 DB 파일 약 3.158GB와 WAL 약 16.4MB를 차지했습니다. 원본 JSON, 인덱스, 구조 테이블을 포함한 대략적인 크기입니다. 동일한 데이터 분포를 단순히 외삽하면 출현 기록당 약 4.8KB이므로 1억 출현 기록은 약 481GB입니다. 당시와 같은 구조당 약 3개 출현 기록을 가진 1억 고유 구조라면 약 1.43TB가 됩니다. 내려받은 원본, 작업 파일, WAL, 백업 공간은 별도로 필요하며, 다른 원천의 필드 크기와 중복률에 따라 크게 달라집니다. 이는 용량 추정이고 검증된 최대치가 아닙니다.

현재 저장 계층은 같은 호스트의 SQLite 한 파일입니다. WAL에서는 읽기와 쓰기가 공존할 수 있지만 동시에 쓰는 주체는 하나이며, 장시간 열린 읽기 트랜잭션은 체크포인트를 지연시킬 수 있습니다. 네트워크 파일시스템에 데이터베이스를 두고 여러 호스트가 같은 WAL 파일을 공유하는 방식도 지원되지 않습니다. [SQLite WAL 공식 문서](https://www.sqlite.org/wal.html)

연결은 `synchronous=NORMAL`을 사용합니다. 성능상 이점이 있지만 갑작스러운 전원 차단·하드 리셋 때 최근 커밋이 되돌아갈 수 있습니다. 원천 파일과 가져오기 보고서로 재실행할 수 있으며, 중요 운영 환경은 백업과 `FULL` 동기화 비용을 검토해야 합니다. [SQLite 동기화 동작](https://www.sqlite.org/wal.html#performance_considerations)

수억 건을 여러 워커·호스트에서 지속적으로 갱신해야 하는 운영 환경에는 원본 압축 파일/Parquet의 객체 저장, 원천·릴리스별 파티션, PostgreSQL 등 동시 쓰기가 가능한 저장 계층, 분산 작업 큐, 검색 인덱스, 체크포인트와 백업 검증을 추가로 설계·부하 시험해야 합니다. 현재 구현이 이미 이 분산 계층을 갖췄다고 주장하지 않습니다. 새로운 계산 후보도 별도의 저장 공간과 검증 단계를 소비하므로 수집된 구조 수만으로 최종 신약 수를 예측할 수 없습니다.
